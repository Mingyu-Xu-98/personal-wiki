Personal Wiki Harness / Architecture Blueprint

个人 Wiki 是意义源，个人网站是编译产物

这个系统不是普通 AI 建站器。它是一个围绕个人知识库持续维护、结构化、验证、版本化的 Harness。 GUI 平台和本地 CLI 都只是入口，真正的核心是同一套 Personal Wiki Engine、Workspace Adapter、Tool Registry 和 Harness Runtime。

业务架构

用户看到的是一个个人网站平台；系统内部实际维护的是个人 Wiki 和构建流水线。

用户价值

把个人知识变成网站

用户维护资料、项目、经历、文章、研究和偏好；系统把这些内容整理为 Wiki，再生成可发布或可导出的个人网站。

  • 不从空白模板开始
  • 网站来自自己的知识库
  • 后续编辑可追溯到版本和来源
平台形态

GUI 托管平台

面向普通用户。提供登录、知识库、创建对话、预览、发布、我的网站和版本管理。Harness 不暴露给用户。

  • 多知识库隔离
  • 对话确认网站需求
  • 发布前预览和继续修改
本地形态

CLI 本地工作区

面向本地资料很多、希望保留文件控制权的用户。CLI 读取本地文件引用，构造 Wiki，并导出静态 HTML。

  • 原始文件默认不复制
  • .pwh/ 保存派生知识和构建产物
  • 网站可作为 HTML 分享

整体用户流程

GUI 和 CLI 的交互方式不同，但底层都走同一条 Wiki -> Harness -> Site 的编译链。

1

选择入口

GUI 用户登录平台；CLI 用户进入本地 workspace。

2

选择知识库

GUI 选择隔离知识库；CLI 读取 .pwh/workspace.json。

3

摄入资料

链接或上传 source，抽取 ontology，生成或更新 Wiki。

4

澄清意图

确认要不要建站，以及网站类型、受众、风格、硬约束。

5

构建验证

Harness 读取 Wiki、调用工具、生成 site plan、编译并验证。

6

版本处理

发布到平台或导出 HTML；保留版本、工具记录和来源引用。

LLM Wiki 工程化

核心不是上传文件后做 RAG，而是把资料维护成持续增长的、可链接、可 lint、可编译的 Wiki。

三层知识结构
Raw Sources不可变证据；LLM 只读；本地默认 file:// 引用。
Ontology Candidates实体、人物、事件、技能、claim、关系，带证据引用。
Persistent Wikiindex.wiki、log.wiki、实体页、概念页、source summary。
Lint And Repair检查孤立页、矛盾、缺引用、过期 source、重复实体。
Compiled Site网站是产物，不能反过来成为知识源。
Ingest

一次摄入是 Wiki Mutation

不是简单摘要。一个 source 可能影响摘要页、实体页、概念页、关系、index 和 log。

Query

先读 Wiki，再读 Source

agent 先读 index，再 searchWiki/readWikiPage，只有需要证据时才 readSource。

Lint

维护是核心能力

知识库越大，越需要定期检查一致性、引用完整性、实体重复和过期内容。

Harness 架构

如果不是模型本身，就是 Harness。Harness 负责节奏、状态、工具、上下文、执行、验证和版本。

Commander
控制阶段和节奏：workspace-discovery、source-linking、ontology-ingest、wiki-maintenance、intent-clarification、site-planning、site-building、verification、versioning、reflection。
Context Ledger
记录本轮使用的 wiki pages、source ids、tool results、model routing、hard/soft constraints 和 preserved refs。
Tool Registry
统一工具边界：readManifest、readWikiIndex、searchWiki、readWikiPage、readSource。工具调用必须写入 ToolCallRecord。
Plan / Execute / Verify
把用户 intent 转成 HarnessPlan，执行工具和内部 handlers，验证是否满足知识来源、隐私、设计、构建和发布约束。
Version / Reflection
生成 BuildVersion，保留 contentModel、sitePlan、toolCalls、lintIssues，并把可复用经验进入 System Meta Skill 候选。

技术架构

核心原则是 GUI 和 CLI 不各自实现一套逻辑，而是共同调用 engine-core。

Entry Points

apps/cliinit/link/ingest/build/status，本地 .pwh 工作区。

harness-coreBuildIntent、HarnessRun、Plan、ToolCallRecord、BuildVersion。

Knowledge Layer

WorkspaceAdapterhosted storage 或 local .pwh。
snapshot.json结构化 Wiki 状态。

builds/dist版本和静态网站产物。

CLI 总指挥流程

CLI 不应该只是命令集合，而应该逐步引导用户完成本地知识库构造，再询问是否基于 Wiki 生成网站。

1

发现工作区

创建或读取 .pwh/，识别 source policy。

2

链接本地文件

保存 file URI、大小、mtime、fingerprint；默认不复制。

3

抽取 Ontology

生成候选实体、事件、技能、claim、关系，并保留 evidence refs。

4

维护 Wiki

更新 source pages、entity pages、index.wiki、log.wiki 和 snapshot。

5

交互确认

询问用户是否要建站；确认类型、受众、风格、隐私边界。

6

构建导出

调用 tools，生成 BuildVersion 和 dist/index.html。

Hard Constraints

硬约束：违反就阻断或询问

  • raw sources 不可修改
  • 知识库必须隔离
  • 本地文件访问必须来自已链接引用
  • 私密内容不能默认发布
  • 构建产物必须版本化
  • 发布必须由用户明确确认
Soft Constraints

软约束：指导质量和品味

  • 不要模板化
  • 保持个人表达，不要营销腔
  • 风格可以随受众调整
  • 信息密度和页面长度可权衡
  • 优先低成本模型处理摘要和小任务
  • 必要时把取舍写入版本说明

Sub Agent 与上下文保真

当前真实 sub agent 数量是 0。目标不是越多越好，而是按阶段启动小而明确的内部角色，并且不靠完整聊天历史传递信息。

目标角色 输入 输出 上下文保真方式
Intent Analyst 用户意图、知识库摘要、硬/软约束 需求结构、缺失问题、确认点 保留用户最终确认和约束 id
Wiki Curator source refs、extracts、现有 index OntologyExtraction、WikiMutationPlan 保留 source/page/entity/tool-call refs
Site Planner wiki index、搜索结果、目标受众 ContentModel、SitePlan、section specs 每个 section 带 sourcePageIds
Content Writer section spec、相关 wiki pages、风格约束 页面文案草稿 保留引用和未解决问题
Verifier 产物、约束、source refs、tool trace lint issues、blocking findings 保留失败证据和修复建议
关键原则：摘要可以有损，引用和产物不能有损。Sub agent 返回 summary 只是为了让主流程快速理解； 真正防丢的是 evidenceRefs、artifact refs、mustCarryForward 和 toolCalls。后续阶段需要细节时必须通过工具重新读取。
